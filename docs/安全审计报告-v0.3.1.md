## 五、架构层面优化总结

### 1. 🔴 缺少统一的鉴权层 (Authentication Layer)

当前系统有三层隔离的安全边界：
- **MCP Server** (stdio/HTTP)：依赖环境变量中的 OKX API Key（仅用于签名 OKX 请求），但 HTTP 模式自身无鉴权
- **Agent Hub** (WS + HTTP)：零鉴权，任何人都可连接
- **Worker 进程**：通过 `spawn` 启动，继承父进程环境变量

**建议**：抽象出统一的 `AuthMiddleware`，应用于所有 HTTP/WS 入口。至少实现 PSK（预共享密钥）机制——所有 Agent 和 Web 客户端必须携带 `Authorization: Bearer <token>` 头或 WS 握手参数。将 `CLAUDE_API_KEY` 和 `OKX_*_KEY` 统一管理在凭证存储层，绝不通过 API 返回。

### 2. 🟡 缺少输入/输出数据契约层 (Data Contract Layer)

当前整个工具链的数据流是：`Zod 参数校验 → okx.ts (unknown 返回值) → 工具 handler (any 强制转换) → LLM Agent (文本)`。中间缺少两层关键防护：
- **API 响应校验**：OKX 返回的数据从不校验结构。如果 OKX API 新增/移除字段，错误会静默传播到 Agent 的推理中
- **输出脱敏**：敏感字段（如 API Key、提现地址）可能意外地通过 `toResult()` 返回给 LLM

**建议**：为核心 API 响应定义 Zod schema，在 `request()` 函数中自动校验。实现一个 `redact()` 函数在 `toResult()` 前自动过滤敏感字段。

### 3. 🔵 Hub 和 MCP Server 耦合度过低导致安全盲区

`hub-server.ts` 和 `index.ts` 各自独立实现了 HTTP 服务器（重复的 CORS 配置、错误处理、404 逻辑），但 `hub-server` 完全不知道 MCP Server 的读/写模式限制。这意味着即使 MCP Server 以只读模式运行，Hub 的 Worker 仍然可以创建/修改文件。

**建议**：将 HTTP 服务器抽象为共享模块 `src/adapters/http-server.ts`。Hub 应在启动时检查 MCP Server 的运行模式，并将读/写能力传递到 Worker 的任务上下文中。Worker 在执行任务前应验证自己的能力边界。

> **审计结论**：代码整体架构设计合理（模块化、关注点分离、错误分类体系完善），但在 **网络安全边界** 方面存在严重缺陷（CORS `*`、API Key 明文泄露、Hub 零鉴权）。建议优先修复致命级 #1-#4，它们构成可被远程利用的攻击链。高级问题中的条件校验缺失（提现地址）和资源管理（fetch 超时、WS 缓冲区）也应尽快处理。
